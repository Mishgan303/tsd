# Лабораторная работа №1
## Технологии хранения больших данных

### Тема
Работа с Apache Airflow. ETL-процесс и сравнительный анализ хранилищ данных.

Источник данных: **Hacker News**.

---

## 1. Цель работы

Цель лабораторной работы — построить ETL-конвейер для сбора, преобразования и загрузки данных Hacker News в несколько различных хранилищ, а затем сравнить эти хранилища по производительности и эксплуатационным характеристикам.

В рамках работы необходимо:

- развернуть Apache Airflow в Docker Compose;
- реализовать не менее трёх ETL-процессов;
- использовать три различных сервиса хранения данных;
- загружать данные в слой ODS;
- провести сравнительный benchmark хранилищ;
- выбрать наиболее подходящее хранилище для дальнейшей работы с данными.

---

## 2. Источник данных

В качестве источника используется **Hacker News**.

Основной ETL получает данные через Hacker News API.

В проекте используются три логически различных набора данных:

- `stories` — публикации Hacker News;
- `comments` — комментарии первого уровня;
- `users` — пользователи, связанные с публикациями.

Для нагрузочного benchmark используется историческая выборка Hacker News из публичного набора данных:

```text
bigquery-public-data.hacker_news.full
```

Выборка содержит **62 872 записи**, то есть примерно 60 тыс. Hacker News stories.


Все сервисы разворачиваются через Docker Compose.

Используемые компоненты:

- **Apache Airflow** — оркестрация ETL-процессов;
- **PostgreSQL ODS** — реляционное хранилище;
- **MongoDB** — документное хранилище;
- **MinIO** — S3-совместимое объектное хранилище;
- **Redis + CeleryExecutor** — выполнение Airflow-задач;
- **служебный PostgreSQL Airflow** — метаданные Airflow.

## 5. ETL-процессы

### 5.1. `stories_etl`

Получает список top stories из Hacker News API, загружает данные каждой публикации и преобразует их к единой структуре:

```text
id
title
author
url
score
descendants
created_at
loaded_at
```

Схема:

```text
extract_stories
       |
       v
transform_stories
       |
       +------------+------------+
       v            v            v
 PostgreSQL       MongoDB       MinIO
```

PostgreSQL и MongoDB используют upsert, поэтому повторный запуск DAG не создаёт дубликаты существующих stories.

---

### 5.2. `comments_etl`

DAG получает комментарии первого уровня для выбранных публикаций Hacker News.

На этапе Transform:

- выбираются прямые комментарии;
- выполняется обработка текста;
- добавляется `profanity_flag`.

После трансформации данные загружаются в PostgreSQL, MongoDB и MinIO.

---

### 5.3. `users_etl`

DAG получает авторов top stories.

На этапе Transform:

- удаляются повторяющиеся пользователи;
- загружаются профили;
- применяется фильтр:

```text
karma >= 1500
```

После этого данные загружаются в PostgreSQL, MongoDB и MinIO.

# 7. Сравнительный benchmark

Для сравнения PostgreSQL, MongoDB и MinIO реализован DAG:

```text
benchmark_db
```

Для benchmark используется фиксированная историческая выборка Hacker News stories из BigQuery.

Размер выборки:

```text
62 872 records
```

Данные приводятся к той же структуре, которая используется в `stories_etl`.

## 8. Схема benchmark

```text
Hacker News historical dataset
            |
            v
       check_dataset
            |
            v
      PostgreSQL test
            |
            v
       MongoDB test
            |
            v
        MinIO test
            |
            v
      collect_results
```

Хранилища тестируются последовательно, чтобы они не конкурировали между собой за CPU, память, диск и сеть.

---

## 9. Критерии сравнения

### Количественные

1. `WRITE` — массовая запись всего набора;
2. `UPSERT` — обновление 10 000 существующих stories;
3. `READ BY ID` — получение одной записи по `id`;
4. `FILTER` — фильтрация по условию `score >= 100`;
5. `FULL READ` — чтение всего набора;
6. `STORAGE SIZE` — занимаемый объём.

### Качественные

7. гибкость схемы;
8. удобство работы.

---

## 10. Методика измерений

Для повышения воспроизводимости каждая операция выполняется несколько раз:

```text
WRITE       -> 3 повтора
UPSERT      -> 3 повтора
READ BY ID  -> 10 повторов
FILTER      -> 10 повторов
FULL READ   -> 5 повторов
```

В итоговый результат записывается медиана времени выполнения.

Время загрузки исходного файла в память в benchmark не входит.

---

## 11. Индексы

### PostgreSQL

```text
PRIMARY KEY(id)
```

### MongoDB

```text
unique index(id)
```

### MinIO

MinIO не является СУБД и не имеет индекса по полям внутри NDJSON-объекта, поэтому поиск по `id` требует последовательного чтения объекта.

---

# 12. Результаты benchmark

| Критерий | PostgreSQL | MongoDB | MinIO |
|---|---:|---:|---:|
| WRITE | 0.372528 s | 0.229138 s | **0.049277 s** |
| UPSERT | **0.059468 s** | 0.140584 s | 0.047273 s* |
| READ BY ID | **0.000066 s** | 0.000093 s | 0.088568 s |
| FILTER | **0.005123 s** | 0.013431 s | 0.165449 s |
| FULL READ | **0.066881 s** | 0.088126 s | 0.167789 s |
| STORAGE SIZE | 17 702 912 B | **3 420 160 B** | 15 722 836 B |

\* В MinIO операция не является настоящим row-level upsert. Для изменения части записей объект перезаписывается целиком.

---

## 13. Анализ результатов

### PostgreSQL

PostgreSQL показал лучшие результаты для операций, типичных для базы данных:

- самый быстрый `READ BY ID`;
- самая быстрая фильтрация;
- самое быстрое полное чтение;
- самый быстрый настоящий row-level upsert.

### MongoDB

MongoDB показала:

- более высокую скорость массовой записи по сравнению с PostgreSQL;
- быстрое чтение по `id`;
- хороший результат фильтрации;
- наименьший физический объём хранения в данном эксперименте.

### MinIO

MinIO показал максимальную скорость массовой записи, так как весь набор сохраняется одним NDJSON-объектом.

При этом для поиска и фильтрации необходимо:

```text
получить объект
      |
      v
прочитать NDJSON
      |
      v
распарсить JSON
      |
      v
найти нужную запись
```

Поэтому MinIO подходит прежде всего для файлов, архивов и raw-данных, а не для частых точечных запросов.

# 14. Гибкость схемы

## PostgreSQL

Для добавления нового поля требуется изменение схемы:

```sql
ALTER TABLE benchmark_stories
ADD COLUMN category TEXT;
```

Преимущества:

- строгие типы;
- ограничения;
- целостность данных.

## MongoDB

Новое поле можно добавить отдельным документам без миграции схемы.

## MinIO

Фиксированной схемы БД нет, но изменение данных внутри существующего объекта требует его перезаписи.

---

# 15. Удобство использования

### PostgreSQL

- SQL;
- индексы;
- JOIN;
- ограничения;
- Primary Key / Foreign Key;
- удобно для дальнейшей нормализации и аналитики.

### MongoDB

- естественное хранение JSON-подобных объектов;
- гибкая структура документов;
- удобно при изменяющейся схеме.

### MinIO

- простой S3 API;
- удобно для файлов и raw-данных;
- высокая скорость последовательной загрузки;
- нет row-level update;
- нет индексов по содержимому объекта;
- фильтрация требует внешнего вычислительного слоя.

---

# 16. Выбор хранилища

Для дальнейшей работы выбрано **PostgreSQL**.

Причины:

1. данные Hacker News имеют структурированную модель;
2. требуется быстрый поиск по идентификаторам;
3. необходима фильтрация;
4. данные обновляются при повторных ETL-запусках;
5. следующая лабораторная требует построения нормализованного DDS;
6. PostgreSQL поддерживает связи, ограничения и JOIN;
7. PostgreSQL показал лучшие результаты на большинстве операций чтения и обновления.

MongoDB остаётся хорошим вариантом для документных данных с меняющейся схемой.

MinIO лучше подходит для хранения сырых файлов, архивов и больших объектов.

---

# 17. Ограничения benchmark

При интерпретации результатов необходимо учитывать:

- PostgreSQL, MongoDB и MinIO используют разные модели хранения;
- MinIO является объектным хранилищем, а не СУБД;
- `STORAGE SIZE` зависит от сериализации, индексов и компрессии;
- MinIO записывает весь набор одним объектом;
- результаты относятся к текущей Docker-конфигурации и используемому оборудованию.

## Итог

В ходе лабораторной работы был реализован ETL-конвейер обработки данных Hacker News с использованием Apache Airflow.

Данные загружаются в три разных типа хранилищ:

- PostgreSQL;
- MongoDB;
- MinIO.

Проведён сравнительный benchmark на фиксированной выборке Hacker News.

Эксперимент показал, что MinIO наиболее эффективен для массовой загрузки объектов, MongoDB удобна для гибких документных структур, а PostgreSQL наиболее подходит для дальнейшей аналитической обработки благодаря высокой скорости запросов, поддержке SQL, индексов, связей и транзакционного обновления данных.

По результатам анализа PostgreSQL выбран как основное хранилище для построения DDS в следующей лабораторной работе.
