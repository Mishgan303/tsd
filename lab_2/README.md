# Отчёт по лабораторной работе №2

## Нормализация данных и Data Quality

## 1. Цель работы

Цель лабораторной работы — разработать детальный аналитический слой данных
DDS на основе PostgreSQL ODS, созданного в первой лабораторной работе.

В ходе работы необходимо:

1. проанализировать исходную структуру данных;
2. выбрать модель DDS: «звезда» или «снежинка»;
3. привести данные к третьей нормальной форме;
4. реализовать очистку, преобразование и обогащение данных;
5. организовать хранение истории изменяющихся показателей;
6. применить SCD там, где необходимо отслеживать версии атрибутов;
7. создать Airflow DAG загрузки ODS → DDS;
8. связать ETL-процессы разных слоёв;
9. создать отдельный DAG проверки качества данных;
10. подготовить запросы для демонстрации полученного DDS.

## 2. Общая архитектура

В первой лабораторной данные Hacker News загружаются в PostgreSQL, MongoDB
и MinIO. По результатам сравнения основным хранилищем для следующих слоёв
выбран PostgreSQL.

ODS и DDS размещаются в одном сервисе `postgres-ods`, но разделяются схемами:

- `public` — ODS первой лабораторной;
- `dds` — детальный аналитический слой второй лабораторной.

Служебная metadata-база Airflow находится в отдельном PostgreSQL-сервисе
`postgres` и не смешивается с аналитическими данными.

```text
Hacker News API
       ↓
ЛР1: stories_etl
       ├── users_etl
       └── comments_etl
       ↓
PostgreSQL ODS: public.stories / public.users / public.comments
       ↓
ЛР2: dds_incremental_etl
       ↓
DDS: измерения / факты-снимки / SCD2
       ↓
dds_data_quality
       ↓
ЛР3: marts_etl
```

`stories_etl` получает top-100 публикаций Hacker News. Затем он запускает
`users_etl` и `comments_etl` с тем же набором `story_ids`. В DDS поступают
публикации, их авторы и комментарии только первого уровня.

## 3. Исходные данные первой лабораторной

ODS хранит последнее загруженное состояние объектов. Повторная загрузка
использует `INSERT ... ON CONFLICT DO UPDATE`, поэтому новая версия объекта
заменяет текущую строку, а не добавляет историю.

### 3.1. Таблица `public.stories`

| `descendants` | `INTEGER` | Общее количество потомков-комментариев |
| `created_at` | `TIMESTAMP` | Время создания публикации |
| `loaded_at` | `TIMESTAMP` | Время последней загрузки строки в ODS |

### 3.2. Таблица `public.users`

Гранулярность: одна строка — последнее состояние одного пользователя.

| Столбец | Тип | Назначение |
|---|---|---|

Гранулярность: одна строка — один комментарий первого уровня.

| Столбец | Тип | Назначение |
|---|---|---|

между таблицами не объявлены, поскольку ODS сохраняет данные близко к форме
источника.

## 4. Выбор модели DDS

Для DDS выбрана учебная схема «снежинка».

Она подходит задаче, потому что:

- стабильные атрибуты отделяются от изменяемых показателей;
- пользователи и публикации представлены отдельными измерениями;
- факты ссылаются на измерения через внешние ключи;
- измерение публикации связано с измерением пользователя;
- история описания пользователя вынесена в отдельную SCD2-таблицу;
- повторение имён авторов и атрибутов публикаций исключается.

Основные связи:

```text
dds.fact_story_snapshot
        │
        ▼
dds.dim_story ───────────────► dds.dim_user
        ▲                           │
        │                           ├──► dds.fact_user_snapshot
        │                           └──► dds.dim_user_profile_history
        │
dds.fact_comment ─────────────► dds.dim_user
```



## 5. Приведение к третьей нормальной форме

### 5.1. Первая нормальная форма

Все значения являются атомарными:

- один автор хранится в одном поле;
- `score`, `karma` и временные метки представлены одним значением;
- массив `submitted` не сохраняется в ячейке, вместо него записывается
  вычисленный `submitted_count`;
- одна строка комментария соответствует одному `comment_id`.

### 5.2. Вторая нормальная форма

В таблицах с составными ключами показатели зависят от ключа целиком:

```text
(user_sk, source_loaded_at)
    → karma, submitted_count, karma_delta, submitted_count_delta

(story_sk, source_loaded_at)
    → score, descendants, score_delta, descendants_delta
```

Значение рейтинга зависит не только от публикации, но и от момента снимка.
Поэтому показатели нельзя переносить только в `dim_story`.

### 5.3. Третья нормальная форма

В DDS устранены транзитивные и повторяющиеся зависимости:

```text
story_id → author_user_sk → данные пользователя
comment_id → story_sk → данные публикации
comment_id → author_user_sk → данные пользователя
```

## 8. Очистка и обогащение

Функции очистки находятся в
[`dags/lib/cleaning.py`](dags/lib/cleaning.py), а загрузка — в
[`dags/lib/incremental.py`](dags/lib/incremental.py).

Реализованы следующие преобразования:

- HTML удаляется из `about` и текста комментариев;
- HTML entities декодируются;
- последовательности пробельных символов заменяются одним пробелом;
- пустые необязательные значения преобразуются в `NULL`;
- пустые обязательные строки приводят к ошибке задачи;
- обязательные числовые значения приводятся к `INTEGER`;
- `bool` не принимается как целое число;
- naive timestamps из ODS интерпретируются как UTC;
- даты сохраняются в DDS как `TIMESTAMPTZ`;
- текстовые имена авторов заменяются суррогатными ключами;
- вычисляются дельты показателей;
- для публикаций рассчитываются фактически загруженные комментарии и
  комментарии с нежелательными словами.

Дельты рассчитываются относительно предыдущего снимка:

```text
karma_delta = current_karma - previous_karma
submitted_count_delta = current_count - previous_count
score_delta = current_score - previous_score
descendants_delta = current_descendants - previous_descendants
```

Для первого снимка соответствующая дельта равна `NULL`.

## 9. Медленно изменяющееся измерение SCD Type 2

SCD Type 2 используется для поля `about` пользователя. История этого поля
важна, потому что его новое значение не должно уничтожать предыдущее.

Алгоритм:

1. найти текущую версию профиля с `valid_to IS NULL`;
2. очистить новое значение `about`;
3. если версия отсутствует — создать первую строку;
4. если значение не изменилось — ничего не записывать;
5. если значение изменилось — установить старой версии `valid_to`;
6. создать новую версию с `valid_from = loaded_at` и `valid_to = NULL`.

Интервал версии трактуется как `[valid_from, valid_to)`. Для одного
пользователя одновременно может существовать только одна открытая версия.

`karma` и `submitted_count` не являются атрибутами SCD2: это числовые
показатели, поэтому они хранятся как факты-снимки.

## 10. Инкрементальная загрузка

DAG `dds_incremental_etl` запускается каждые 8 часов:

```python
schedule="0 */8 * * *"
```

Для `stories`, `users` и `comments` поддерживаются независимые watermark.
В начале запуска фиксируется верхняя граница:

```text
captured_max = max(public.<source>.loaded_at)
```

Затем обрабатывается интервал:

```text
(last_processed_at, captured_max]
```

Левая граница не входит в окно, потому что она уже была обработана. Правая
граница входит, чтобы не потерять строки, существовавшие в момент фиксации
окна.

Если строка обновится после фиксации `captured_max`, её новый `loaded_at`
окажется за правой границей и попадёт в следующий запуск.

Через XCom передаются только три небольших объекта с границами окон. Сами
строки читаются задачами непосредственно из PostgreSQL.

двумя запусками.

## 12. Зависимости между ETL-процессами

Для связи DAG используется `TriggerDagRunOperator`.

В первой лабораторной `stories_etl` запускает:

```text
stories_etl
  ├── users_etl
  └── comments_etl
```

Вторая лабораторная после формирования DDS запускает:

```text
dds_incremental_etl
  → dds_data_quality
  → marts_etl
```

Для дочерних запусков используется `wait_for_completion=True`, поэтому
родительский DAG продолжает выполнение только после их успешного завершения.
В `dds_data_quality` передаются `source_run_id` и зафиксированные окна
источников.

Если DQ или публикация витрин завершается ошибкой, watermark не перемещается.
Следующий запуск снова увидит тот же интервал и безопасно повторит его.

## 13. Идемпотентность и транзакции

Повторный запуск не должен создавать дубликаты или пропускать данные.

Идемпотентность обеспечивают:

- `CREATE ... IF NOT EXISTS` для объектов схемы;
- `UNIQUE` для естественных ключей;
- составные первичные ключи фактов-снимков;
- `INSERT ... ON CONFLICT DO NOTHING` для неизменяемого grain;
- `INSERT ... ON CONFLICT DO UPDATE` для измерений Type 1 и DQ-результатов;
- watermark, который обновляется только после успешной цепочки;
- одна транзакция внутри каждой функции загрузки;
- `rollback` при исключении.

Успешные задачи DDS выполняются отдельными транзакциями. Если последующая
DQ-проверка падает, ранее записанные строки остаются в DDS, но watermark не
изменяется. Повторная обработка безопасна благодаря первичным ключам и
`ON CONFLICT`.

## 14. Data Quality

Отдельный DAG расположен в
[`dags/dds_data_quality.py`](dags/dds_data_quality.py), а реализация проверок —
в [`dags/lib/quality.py`](dags/lib/quality.py).

DAG не имеет собственного расписания:

```python
schedule=None
```

Он запускается из `dds_incremental_etl`, выполняет проверки, сохраняет каждый
результат в `dds.data_quality_results` и только после этого определяет общий
статус.

### 14.1. Реализованные проверки

| Проверка | Что контролируется | Тип |
|---|---|---|
| `completeness.required_values` | Обязательные ключи и показатели не `NULL` и не пусты | Блокирующая |
| `uniqueness.natural_and_snapshot_keys` | Нет повторов естественных и составных ключей | Блокирующая |
| `referential_integrity.orphan_facts` | Все внешние ключи разрешаются в измерения | Блокирующая |
| `validity.non_negative_measures` | Счётчики, `score` и `descendants` неотрицательны | Блокирующая |
| `validity.timestamps_not_in_future` | Временные метки не находятся в будущем | Блокирующая |
| `scd2.single_open_version` | У пользователя не более одной открытой версии | Блокирующая |
| `scd2.non_overlapping_intervals` | Интервалы SCD2 не пересекаются | Блокирующая |
| `reconciliation.ods_users_to_dds` | Все обработанные пользователи представлены в DDS | Блокирующая |
| `reconciliation.ods_stories_to_dds` | Все обработанные публикации представлены в DDS | Блокирующая |
| `reconciliation.ods_comments_to_dds` | Все обработанные комментарии представлены в DDS | Блокирующая |
| `history.snapshot_key_uniqueness` | Retry не создаёт повторный grain снимка | Блокирующая |
| `anomaly.comment_counts` | `bad_word ≤ loaded comments ≤ descendants` | Предупреждение |

Отрицательная `karma` не считается ошибкой качества, потому что Hacker News
может возвращать её для наказанных пользователей.

Проверка количества комментариев является предупреждением. API публикаций и
комментариев читается несколькими HTTP-запросами без общей транзакции, поэтому
состояние `descendants` может измениться между запросами.

### 14.2. Поведение при нарушении качества

1. Все проверки выполняются независимо.
2. Результаты сохраняются в `dds.data_quality_results`.
3. Если нарушена блокирующая проверка, поднимается `DataQualityError`.
4. DAG `dds_data_quality` получает состояние `failed`.
5. `dds_incremental_etl` не запускает следующий шаг и не перемещает watermark.

## 16. Вывод

Во второй лабораторной работе сырые операционные данные первой лабораторной
преобразованы в нормализованный детальный аналитический слой DDS. Реализована
схема «снежинка», в которой измерения пользователей и публикаций отделены от
исторических фактов-снимков. Данные приведены к 3НФ, связи закреплены внешними
ключами, а история профиля хранится по SCD Type 2.

Инкрементальная обработка выполняется отдельными окнами для трёх ODS-
источников. Watermark, ограничения и операции `ON CONFLICT` обеспечивают
безопасный повторный запуск. Отдельный DAG Data Quality контролирует
заполненность, уникальность, ссылочную целостность, допустимость значений,
SCD2-инварианты и соответствие ODS → DDS. Полученный слой используется как
источник для аналитических витрин третьей лабораторной работы.
